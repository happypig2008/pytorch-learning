# 任务二：OKTI 图像压缩与解压 开发报告
## 一、 错误解决记录（踩坑与排错过程）

在开发过程中，我遇到了以下几个核心错误，通过排查最终得以解决：

1. **文件扩展名导致的 `FileNotFoundError`**
   - **现象**：代码开始运行报错，找不到 `small.okti`。
   - **排查**：检查左侧目录，发现 PyCharm 新建文件时自动加了 `.py` 后缀，变成了 `small.okti.py`。
   - **解决**：手动重命名为 `small.okti`，成功读取。这让我明白**输入文件类型必须和代码预期完全一致**。

2. **`IndexError: image index out of range` 坐标越界**
   - **现象**：画图时程序崩溃，提示坐标越界。
   - **排查**：发现 `pixel_count` 在计算坐标前就自增了，导致坐标提前越界。
   - **解决**：调整代码顺序为 **“先计算 `x,y` 坐标 -> 再绘图 `putpixel` -> 最后 `pixel_count += 1`”**，问题解决。

3. **`ValueError: invalid literal for int()` 切片与输入错误**
   - **现象**：解析 `d` 类型时因长度不对报错；后来又出现 `'oo'` 无法转为十六进制。
   - **排查**：第一个是复制了 `p` 类型的切片导致长度不符；第二个是我手动输入测试文件时，把数字 `0` 打成了字母 `o`。
   - **解决**：正确修改 `d` 类型的切片长度；同时严格校验 `.okti` 测试文件内容，确保只有 0-9 和 a-f 的十六进制字符。

4. **Git 推送网络超时（`Connection was reset`）**
   - **现象**：本地 Commit 成功，但 Push 到 GitHub 失败。
   - **排查**：校园网和热点都存在连接不稳。原因是本次重构文件变动大，Git 分块传输易被拦截。
   - **解决**：使用 `git config --global http.postBuffer 524288000` 扩大传输缓冲区，并切换手机热点成功推送。

## 二、 个人优化方案（拓展功能设计）

为了让程序不仅“能跑”，还要“好用”，我主动做了以下优化：

1. **智能路径查找（解决用户痛点）**
   - **初衷**：用户不该每次都要输入冗长的 `../tests/valid/small.okti`。
   - **方案**：引入 `os` 模块，实现自动拼接路径。用户只需输入 `small.okti`，程序自动去 `valid` 找，找不到再去 `invalid` 找；如果用户输入完整路径（如桌面文件），则直接读取。
   
2. **工程化目录重构**
   - **初衷**：前期代码和测试文件全部平铺在根目录，极其混乱。
   - **方案**：建立 `src/`（代码）、`tests/`（正确/错误测试集）、`outputs/`（生成图片）、`docs/`（笔记文档）四大模块，并添加 `.gitignore` 忽略无用文件。这使得项目具备了良好的可维护性。

3. **完善的命令行交互**
   - **初衷**：单一运行方式不够灵活。
   - **方案**：结合 `sys.argv`，支持命令行传参运行，也支持无参数时通过 `input()` 提示输入，兼容性更强。

## 三、 AI 使用说明与心得
- **AI 帮了我什么**：帮我理清了复杂的坐标计算逻辑，提供了 `Pillow` 库的使用示例，以及在网络排错时提供了 Git 缓冲区扩容的思路。
- **AI 的局限**：AI 无法替我检查文件内容的准确性（导致我犯了 `oo` 和 `00` 的错），也无法替我在 PyCharm 里重命名文件或解决网络连接问题。
- **我的心得**：AI 只是助教，代码的最终质量和逻辑必须由我亲自把关。我坚持做到了**“每一行代码都理解、每一次报错都记录、每一个问题都自主验证”**。
