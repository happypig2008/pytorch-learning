# 任务二：OKTI 图像压缩与解压 开发报告

## 一、 错误解决记录（踩坑与排错过程）

### （一）编码器阶段（图像压缩）
1. **`FileNotFoundError: 'test.png'`（文件找不到）**
   - **现象**：程序刚跑就崩溃，提示找不到文件。
   - **排查**：Python 默认在当前运行目录 `src` 下找文件，而图片放在 `outputs` 目录里。
   - **解决**：引入 `os` 模块，编写 `find_image_file` 函数，自动在 `src`、`outputs` 以及上一级目录中搜索，避免硬编码路径。

2. **`'PhotoImage' object has no attribute 'getWidth'`（API 错误）**
   - **现象**：尝试获取图片宽高时，提示对象没有此属性。
   - **排查**：查阅 `SimpleGraphics.py` 源码，发现 `loadImage` 返回的是 Tkinter 的 `PhotoImage` 对象，不是我们以为的普通对象。
   - **解决**：改用 `image.width()` 和 `image.height()`，像素读取改用 `image.get(x, y)`。

3. **`int() can't convert non-string with explicit base`（类型错误）**
   - **现象**：处理像素颜色时，转十六进制报错。
   - **排查**：AI 给我的代码误以为 `image.get()` 返回字符串（如 `'#ff0000'`），但实际上它返回的是 `(r, g, b)` 整数元组。
   - **解决**：直接解包 `r, g, b = image.get(x, y)`，不再手动转字符串。

4. **PNG 透明通道导致转换异常**
   - **现象**：遇到带透明背景的 PNG 时，转 PPM 会丢失数据或报错。
   - **解决**：在 `convert_to_ppm.py` 和 `ensure_ppm_format` 中加入 `img.convert('RGB')`，强制丢弃 Alpha 通道，转化为标准 RGB 格式。

5. **压缩率统计为负数（-71.85%）**
   - **现象**：对比 `differences_small.png`（原始 373 字节）和生成的 `output.okti`（641 字节），体积反而变大了。
   - **分析**：OKTI 是纯文本格式，每行末尾有换行符（占 1 字节）。对于只有 120 个像素的超小图，换行符的开销远大于编码节省的空间。这不是 Bug，而是纯文本编码的局限性，在大图片上压缩率会回归正常。

### （二）解码器阶段（图像还原）
6. **`IndexError: image index out of range`（坐标越界）**
   - **现象**：画图时程序崩溃，提示像素坐标越界。
   - **排查**：计算像素位置时，`pixel_count` 在计算坐标前就自增了，导致第一张图判断错误。
   - **解决**：调整代码顺序为 **“先计算 `x,y` 坐标 -> 再绘图 `putpixel` -> 最后 `pixel_count += 1`”**，问题解决。

7. **`ValueError: invalid literal for int()`（切片与输入错误）**
   - **现象**：解析 `d` 类型时长度不符报错，后来又出现 `'oo'` 无法转换的报错。
   - **排查**：第一个是复制了 `p` 类型的切片长度；第二个是我手动输入测试文件时，把数字 `0` 误打成了字母 `o`。
   - **解决**：修正 `d` 类型的切片长度；同时严格校验 `.okti` 测试文件内容，确保只有 `0-9` 和 `a-f`。

### （三）开发工具与网络
8. **PyCharm 自动加后缀导致找不到文件**
   - **现象**：新建文件时，文件名变成了 `small.okti.py`。
   - **解决**：手动重命名为 `small.okti`，明白**输入文件类型必须和代码预期完全一致**。

9. **`Connection was reset`（Git 推送网络超时）**
   - **现象**：本地 Commit 成功，但 Push 到 GitHub 失败。
   - **排查**：校园网和热点对 GitHub 连接都不稳，分块传输容易被拦截。
   - **解决**：直接登录 GitHub 网页，使用“Upload files”拖拽上传，成功完成提交。

## 二、 个人优化方案（拓展功能设计）

为了让程序不仅“能跑”，还要“好用”，我主动做了以下优化：

1. **智能路径查找（解决用户痛点）**
   - **初衷**：用户不该每次都要输入冗长的 `../outputs/test.ppm`。
   - **方案**：引入 `os` 模块，实现自动拼接路径。用户只需输入 `small`，程序自动去对应目录找 `.ppm` 或 `.png`，找不到再逐层向上找。

2. **工程化目录重构**
   - **初衷**：前期代码和测试文件全部平铺在根目录，极其混乱。
   - **方案**：建立 `src/`（代码）、`tests/`（测试集）、`outputs/`（生成文件）、`docs/`（笔记文档）四大模块，并添加 `.gitignore` 忽略无用文件。这使得项目具备了良好的可维护性。

3. **完善的命令行交互**
   - **初衷**：单一运行方式不够灵活。
   - **方案**：结合 `sys.argv`，支持命令行传参运行，也支持无参数时通过 `input()` 提示输入，兼容性更强。

4. **自动格式转换与编码统计（新增拓展）**
   - **初衷**：方便统计编码效率，同时免去手动转换格式的麻烦。
   - **方案**：检测到 `.png` 自动调用 Pillow 转为 `.ppm`；在 `encode_image` 中增加计数器，输出每种编码（p/d/r/R/i/I）的使用次数，方便评估压缩效果。

- **AI 帮了我什么**：帮我理清了复杂的 `d` 差值偏置计算逻辑，提供了 `Pillow` 库的使用示例，以及在网络排错时提供了 Git 缓冲区扩容的思路。
- **AI 的局限与错误**：AI 无法替我检查文件内容的准确性（导致我犯了 `oo` 和 `00` 的错）；AI 也无法替我解决环境的 API 差异（比如 `getWidth` 报错，最后是我自己看源码解决的）。
